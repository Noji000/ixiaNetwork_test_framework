0InstanceId Bug 修复补丁

问题现象

在 IxNetwork 9.20 环境下，使用 RestPy 修改 Traffic Stack Field 属性时（如 field.ValueType = 'increment'），服务端返回 400 BadRequestError: InstanceId is not a string。

错误堆栈 
BadRequestError: InstanceId is not a string
System.Exception: InstanceId is not a string
   at SDMCsLib.SDMObjIdPiece.GetIdAsString()
   at IxNetwork.Traffic2.Publishers.StackFieldHandler.Find(...)
   at SDMHelpers.WalkContext.walkTo(...)
   at SDMCsLib.RestService.SdmObject.Patch()
   at SDMCsLib.RestService.V1ObjectController.Patch(String path)

根因分析

RestPy 的 Base._update() 方法在构造 PATCH 请求时，自动将对象的 id 字段放入 payload body 中，并将请求发送到集合端点（如 /stack/1/field），而非具体资源端点（如 /stack/1/field/1）。

IxNetwork 服务端的 StackFieldHandler.Find() 在解析 payload body 中的 id 字段时，调用 SDMObjIdPiece.GetIdAsString() 试图将其转为字符串，但该字段在此上下文中不是合法的 SDM 对象 ID 格式，导致异常。

来源 该问题在 OpenIxia GitHub Issue #138 中有完整记录，用户在修改 Ethernet Destination MAC 字段时触发完全相同的错误 [$TRAE_REF](https://github.com/OpenIxia/IxNetwork/issues/138)。

调试发现

通过在 Connection._update 层面拦截 PATCH 请求，捕获到实际的 HTTP 请求内容：

# 实际发送的 PATCH 请求
# href: 集合端点（不包含具体 field id）
PATCH /api/v1/sessions/1/ixnetwork/traffic/trafficItem/1/configElement/1/stack/1/field

# payload: id 在 body 中
{
  "valueType": "increment",
  "id": "1"       # ← StackFieldHandler 无法解析
}

修复方案

Monkey-patch Connection._update：如果 payload 中包含 id 字段，则将其从 payload 中移除，并拼接到 URL 路径中，变为对具体资源端点的 PATCH。

import ixnetwork_restpy.connection as conn_mod

_original_conn_update = Connection._update

def _patched_conn_update(self, href, payload):
    if isinstance(payload, dict) and 'id' in payload:
        # 将 id 移到 URL 路径中
        obj_id = payload['id']
        item_href = href.rstrip('/') + '/' + str(obj_id)
        new_payload = {k: v for k, v in payload.items() if k != 'id'}
        return _original_conn_update(self, item_href, new_payload)
    elif isinstance(payload, list):
        new_payload = [
            {k: v for k, v in item.items() if k != 'id'}
            if isinstance(item, dict) and 'id' in item else item
            for item in payload
        ]
        return _original_conn_update(self, href, new_payload)
    return _original_conn_update(self, href, payload)

Connection._update = _patched_conn_update
修复效果 修复后的 PATCH 请求变为：PATCH /stack/1/field/1 + payload {"valueType": "increment"}，服务器从 URL 路径直接识别资源，绕过 StackFieldHandler.Find() 的解析问题。

来源：GitHub Issue #138 - Ethernet destination field cannot be updated [$TRAE_REF](https://github.com/OpenIxia/IxNetwork/issues/138)；RestPy Connection 源码 [$TRAE_REF](https://github.com/OpenIxia/ixnetwork_restpy/blob/master/ixnetwork_restpy/connection.py)；Field 类源码 [$TRAE_REF](https://github.com/OpenIxia/ixnetwork_restpy/blob/master/ixnetwork_restpy/testplatform/sessions/ixnetwork/traffic/trafficitem/configelement/stack/field/field.py)

3L1Config 配置 (100G + RS-FEC)

根据硬件类型获取对应的 L1Config 对象，配置速率为 100G 并启用 RS-FEC。

# L1Config 类型映射表
CTYPE_MAP = {
    "tenFortyHundredGigLan": "TenFortyHundredGigLan",
    "novusHundredGigLan": "NovusHundredGigLan",
    "uhdOneHundredGigLan": "UhdOneHundredGigLan",
    # ... 其他类型
}

def get_l1(vport):
    ctype = vport.L1Config.CurrentType
    prop = CTYPE_MAP.get(ctype, ctype)
    return getattr(vport.L1Config, prop)

# 使用 BatchUpdate 批量提交
with BatchUpdate(ixnetwork):
    for vp in (tx, rx):
        l1 = get_l1(vp)
        l1.Speed = "speed100g"
        l1.SelectedSpeeds = ["speed100g"]
        l1.IeeeL1Defaults = False        # 取消 IEEE Media defaults
        l1.EnabledFlowControl = False     # 取消 Flow Control
        l1.LaserOn = True
        l1.EnableAutoNegotiation = True
        l1.EnableRsFec = True             # 启用 RS-FEC
L1Config 属性设置值说明
Speedspeed100g链路速率 100G
SelectedSpeeds["speed100g"]可选速度列表
IeeeL1DefaultsFalse不使用 IEEE Media 默认值
EnabledFlowControlFalse禁用流控
EnableRsFecTrue启用 RS-FEC（前向纠错）
EnableAutoNegotiationTrue启用自协商
LaserOnTrue开启激光器
BatchUpdate BatchUpdate 是 RestPy 的批量提交助手，可将多个属性修改合并为一次 REST call，显著减少网络开销。在 with 块退出时自动提交（commit）。

4.3 添加 IPv4 协议头 (ProtocolTemplate + Append)

使用官方 createTrafficItemAddPacketHeader.py 示例的标准写法：先获取 ProtocolTemplate，再通过 Stack.Append() 追加到已有 Stack 之后。

def createPacketHeader(trafficItemObj, packetHeaderToAdd=None, appendToStack=None):
    configElement = trafficItemObj.ConfigElement.find()[0]
    # 1. 获取协议模板
    protocolTemplate = ixnetwork.Traffic.ProtocolTemplate.find(
        StackTypeId=packetHeaderToAdd
    )
    # 2. 找到要追加的位置
    appendToStackObj = configElement.Stack.find(StackTypeId=appendToStack)
    # 3. 用 Append 方法添加
    appendToStackObj.Append(Arg2=protocolTemplate)
    # 4. 获取新添加的 Stack
    newStack = configElement.Stack.find(StackTypeId=packetHeaderToAdd)
    return newStack.Field

# 添加 IPv4（追加到 Ethernet 之后）
ipv4FieldObj = createPacketHeader(
    traffic_item,
    packetHeaderToAdd='ipv4',
    appendToStack='ethernet$',
)

# 源 IP（递增）
ipv4SrcField = ipv4FieldObj.find(DisplayName='Source Address')
ipv4SrcField.ValueType = 'increment'
ipv4SrcField.StartValue = '1.1.1.1'
ipv4SrcField.StepValue = '0.0.0.1'
ipv4SrcField.CountValue = 1

# 目的 IP（列表）
ipv4DstField = ipv4FieldObj.find(DisplayName='Destination Address')
ipv4DstField.ValueType = 'valueList'
ipv4DstField.ValueList = ['1.1.1.2', '1.1.1.3', '1.1.1.4', '1.1.1.5']

4.4 添加 TCP 协议头

同样使用 createPacketHeader 函数，将 TCP 追加到 IPv4 之后。

# 添加 TCP（追加到 IPv4 之后）
tcpFieldObj = createPacketHeader(
    traffic_item,
    packetHeaderToAdd='tcp',
    appendToStack='ipv4',
)

# 源端口（递增）
tcpSrcPortField = tcpFieldObj.find(DisplayName='TCP-Source-Port')
tcpSrcPortField.ValueType = 'increment'
tcpSrcPortField.StartValue = '1024'
tcpSrcPortField.StepValue = '1'
tcpSrcPortField.CountValue = 1

# 目的端口（列表）
tcpDstPortField = tcpFieldObj.find(DisplayName='TCP-Dest-Port')
tcpDstPortField.ValueType = 'valueList'
tcpDstPortField.ValueList = ['80', '443', '8080', '22']
DisplayName 命名规则 TCP 字段的 DisplayName 使用 带前缀 格式：TCP-Source-Port 和 TCP-Dest-Port，而非 Source-Port / Destination-Port。错误的 DisplayName 会导致 find() 返回空列表，后续属性赋值触发 IndexError: list index out of range。建议添加协议后先遍历打印所有 Field 的 DisplayName 确认正确名称。

注意事项

1. InstanceId is not a string（核心 Bug）

在 IxNetwork 9.20 及更早版本中，RestPy 修改 Traffic Stack Field 属性时会触发此错误。根因是 RestPy 将 id 放入 PATCH payload body 而非 URL 路径，服务端 StackFieldHandler.Find() 无法解析。必须安装 Step 0 的 monkey-patch 补丁才能正常工作。该问题在 GitHub Issue #138 中有记录 [$TRAE_REF](https://github.com/OpenIxia/IxNetwork/issues/138)。

2. DisplayName 命名不统一

不同协议层的 Field DisplayName 命名规则不一致：

  • Ethernet: Destination MAC Address / Source MAC Address
  • IPv4: Source Address / Destination Address
  • TCP: TCP-Source-Port / TCP-Dest-Port（带 TCP- 前缀）

使用错误的 DisplayName 不会报错，但 find() 返回空列表，后续属性赋值会触发 IndexError。建议添加新协议后先遍历所有 Field 打印 DisplayName 确认。

3. StackTypeId 通配符

Ethernet 的 StackTypeId 是 ethernet$（带 $ 后缀），而 IPv4 和 TCP 分别是 ipv4 和 tcp（不带 $）。在 Stack.find(StackTypeId=...) 和 appendToStack 参数中必须使用正确的值。

4. Apply 与 Start 顺序

修改 TrafficItem 后服务端会产生 [Traffic Generate required] 警告。必须调用 Traffic.Apply() 下发配置后才能 Start()，否则流量不会按新配置发送。

5. IgnoreLinkUp 的影响

IgnoreLinkUp=True 允许在物理链路未 Up 时继续执行。此时端口状态为 connectedLinkDown，流量虽然可以 Apply 但不会真正发送。如果看到 TxFrames=0 且 RxValid=0，应检查物理链路是否就绪。正常 Link Up 后端口状态为 connectedLinkUp。

6. BatchUpdate 与 Field 属性赋值

BatchUpdate 适用于 L1Config 等属性的批量提交。但 Traffic Stack Field 的属性赋值（field.ValueType = '...'）会立即触发单独的 PATCH 请求，不能被 BatchUpdate 延迟。monkey-patch 必须在 Field 属性赋值之前安装。

7. 系统内存监控

IxNetwork 服务端在内存不足时会发出 [System's available memory is very low] 警告。如果系统可用内存低于 10%，应先清理不必要的配置或重启 session 再继续操作，避免服务端崩溃。

8. ProtocolTemplate.find() 匹配方式

获取协议模板时使用 StackTypeId 参数（如 'ipv4'、'tcp'），而非 DisplayName。部分旧示例脚本使用 DisplayName='TCP' 的写法，在较新版本中可能匹配不到，推荐统一使用 StackTypeId。

9. 端口统计读取时机

启动流量后需要等待一段时间（如 10 秒）让计数器积累，否则可能读到 0 值。StatViewAssistant 的 Timeout 参数控制等待视图就绪的最长时间，不是等待流量发送的时间。
